## P1 — HIGH: ยื่นใบลาไม่ได้ทุกกรณี และหน้าเว็บแสดง error ดิบของฐานข้อมูล

ผู้ใช้ทุกคนยื่นใบลาไม่ได้ และบันทึกแบบร่างก็ไม่ได้ ข้อความที่ผู้ใช้เห็นเป็นข้อความ exception ของ PostgreSQL ซึ่งเปิดเผยชื่อ constraint ภายในระบบ ทำซ้ำได้ 5 ครั้งจาก 5 ครั้ง (ลากิจส่งจริง 2 ครั้ง, ลาป่วยส่งจริง 2 ครั้ง, บันทึกแบบร่าง 1 ครั้ง) และไม่มีข้อมูลถูกสร้างขึ้น (หน้า "ประวัติเอกสาร" ยังว่าง)

**ขั้นตอนทำซ้ำ** (ล็อกอินเป็น `hr`)
1. เมนู ยื่นเอกสาร → ยื่นคำขอลา (`/documents/leave`)
2. ประสงค์ขอลา = ลาป่วย, เหตุผล = `QA test - please ignore`
3. วันที่ลา = 19/10/2569 ถึง 19/10/2569 (ช่องแสดง "มีกำหนด 1 วัน", โควตา "ใช้ได้อีก 30 วัน" ถูกต้อง)
4. กด "ยื่นคำขอลา" รอประมาณ 10 วินาที
5. จะมีแถบแดงด้านบนฟอร์มแสดงข้อความ error ด้านล่าง (กด "บันทึกแบบร่าง" ก็ได้ผลเหมือนกัน)
6. ทดสอบเพิ่ม: ลากิจส่วนตัว 12–14/10/2569 (ระบบคำนวณ "2 วัน (ไม่นับวันหยุด 1 วัน)" ถูกต้อง เพราะ 13 ต.ค. เป็นวันหยุดบริษัท) ก็ล้มเหลวเหมือนกัน

**Request**
```
POST http://26.169.162.24:5229/api/leave-requests/my   -> 400  (ใช้เวลา ~9-10 วินาที)
{"leaveTypeId":2,"startDatetime":"2026-10-18T17:00:00.000Z","endDatetime":"2026-10-19T16:59:59.000Z","leaveHours":8,"leaveDays":1,"reason":"QA test - please ignore","saveAsDraft":false}
```
กรณีบันทึกแบบร่าง ส่ง body เดิมแต่ `"saveAsDraft":true` ได้ผลเหมือนกัน

**Response**
```
{"success":false,
 "message":"23505: duplicate key value violates unique constraint \"leave_request_request_no_key\"\r\n\r\nDETAIL: Detail redacted as it may contain sensitive data. Specify 'Include Error Detail' in the connection string to include this information.",
 "data":null,"errors":[]}
```

**ก่อนหน้านั้น** การเรียก `GET /api/leave-requests/calculate-days?startDate=2026-10-12&endDate=2026-10-14&halfDay=false` → 200 และ `POST /api/leave-requests/my/validate` → 200 (ผ่าน) แสดงว่าปัญหาอยู่ตอน insert ใบลา

**ผลที่ควรเป็น**
- ยื่นใบลาได้ และได้เลขที่ใบลาใหม่ที่ไม่ซ้ำ
- ถ้ามีข้อผิดพลาดจริง ให้แสดงข้อความภาษาไทยที่เข้าใจง่าย ห้ามส่ง exception ของฐานข้อมูลมาถึงหน้าเว็บ

**จุดที่น่าจะต้องดู (ฝั่ง backend)**
- ตรรกะสร้าง `request_no` ของ `leave_request`: น่าจะสร้างเลขซ้ำกับแถวที่มีอยู่แล้ว (เช่น คำนวณจาก COUNT หรือ MAX+1 แล้วชนกับข้อมูลที่ถูกลบ/ข้อมูลเก่า หรือ sequence ตามหลังข้อมูลที่ seed ไว้) ให้ใช้ sequence ของฐานข้อมูลหรือ retry เมื่อชน
- ใบรับรอง (`certificate`) ยื่นได้ปกติ (ได้เลข CERT-4) ดังนั้นปัญหาเฉพาะตารางใบลา
- แก้ให้ middleware/exception handler ไม่ส่ง `message` ดิบของ DB ออกไป (บันทึกลง log ฝั่ง server แทน)
- ฝั่ง frontend: ควรแสดงข้อความ error ที่ปลอดภัยแทนการแสดง `response.message` ตรง ๆ

**ตรวจหลังแก้**: ยื่นใบลาลาป่วย 1 วัน ต้องสำเร็จและขึ้นในหน้า `/documents/history` ด้วยสถานะ "รออนุมัติ"; ยื่นซ้ำหลายครั้งต้องได้เลขที่ไม่ซ้ำ; บันทึกแบบร่างต้องสำเร็จ

### P2-3 หน้ารายละเอียดพนักงาน: timeout ถูกแสดงเป็น "ไม่พบข้อมูลพนักงาน" ทับข้อมูลที่โหลดสำเร็จแล้ว
1. ล็อกอินเป็น `admin` → พนักงาน → คลิกชื่อ "นางสาว HR Syaco" (`/employees/2`)
2. หน้าแสดงข้อมูลได้ตามปกติ (เมื่อ `GET /api/employees/2` ตอบกลับ ~5.6 วินาที)
3. รอสักครู่ หน้าเปลี่ยนเป็นหน้า "ไม่พบข้อมูลพนักงาน — เซิร์ฟเวอร์ใช้เวลาประมวลผลนานเกินไป (timeout) ข้อมูลอาจถูกบันทึกแล้ว กรุณารีเฟรชหน้าเพื่อตรวจสอบ" (พบ 1 ครั้งในการทดสอบ ขึ้นกับความช้าของ API จึงอาจไม่เกิดทุกครั้ง)
4. Network: คำขอ `GET /api/employees/:id` ถูกเรียก 2 ครั้ง ครั้งแรกสำเร็จ (~5.6s) ครั้งที่สองถูกตัดที่ 15 วินาที (status 0). Console: `Failed to load employee details: AxiosError ... handleTimeout`

ปัญหาสองข้อซ้อนกัน
- (a) หน้าเรียกข้อมูลซ้ำสองครั้ง (น่าจะเป็น `useEffect` ที่ทำงานสองรอบ) และผลของครั้งที่ล้มเหลวไปทับครั้งที่สำเร็จ
- (b) ข้อความ timeout ที่ใช้กับทุกคำขอ รวมถึง GET พูดว่า "ข้อมูลอาจถูกบันทึกแล้ว" ซึ่งไม่สมเหตุสมผลกับการอ่านข้อมูล และหน้า error ใช้หัวข้อ "ไม่พบข้อมูลพนักงาน" ทั้งที่เป็น timeout ไม่ใช่ 404
อาการเดียวกันใน console ของ `/profile` ("Failed to load profile") และ `/leave-balances` ("Failed to load leave balance summary")

**ผลที่ควรเป็น**: ถ้าเคยโหลดสำเร็จแล้ว ห้ามเขียนทับด้วย error ของคำขอซ้ำ; แยกข้อความ timeout (มีปุ่ม "ลองใหม่") ออกจาก "ไม่พบข้อมูล" (404); ข้อความ "ข้อมูลอาจถูกบันทึกแล้ว" ใช้เฉพาะ POST/PUT/DELETE
**จุดที่น่าจะต้องดู**: interceptor ของ axios (ที่สร้าง timeout message), `EmployeeDetailPage` `useEffect.fetchEmployee` (ต้องมี cleanup/abort และไม่ setState เมื่อมีข้อมูลแล้ว)

**ผลที่ควรเป็น**: แยกที่อยู่ลงช่องที่ถูกต้อง (หรือแสดงเป็นบรรทัดเดียวถ้าไม่มีการแยก) และแปลง `CURRENT` เป็นป้ายภาษาไทย

### P2-5 แดชบอร์ดโชว์โควตาลาค่าเริ่มต้นก่อนข้อมูลจริงมา (ผู้ใช้เห็นตัวเลขผิดนาน ~20 วินาที)
เปิด `/` (หลังเข้าจากหน้าอื่นผ่านเมนู) ตัวเลขบนการ์ดลา: ลาป่วย 0/30, ลากิจ 0/3, **ลาพักร้อน 0/6**, ลาพิเศษ 0/10 แสดงตั้งแต่วินาทีแรก จนถึงประมาณวินาทีที่ 22 จึงเปลี่ยนเป็น **ลาพักร้อน 0/10** (ค่าจริงจาก `GET /api/leave-balances/my-summary?year=2026&employeeId=1`, ใช้เวลา 9–15 วินาที บางครั้งถูกตัดด้วย timeout) หน้า `/leave-balances` ให้ค่าจริง พักร้อน 0/10 เหมือนกัน ดังนั้นค่า 0/6 คือค่าเริ่มต้นตายตัวที่ผิด
**ผลที่ควรเป็น**: ระหว่างรอข้อมูลให้แสดง skeleton หรือ "-" แทนตัวเลขเริ่มต้น เพราะพนักงานที่มีสิทธิ์พักร้อนจริง 10 วัน จะเห็นว่าเหลือ 6
**จุดที่น่าจะต้องดู**: state เริ่มต้นของ summary ในหน้า dashboard

### P2-6 หน้าข้อมูลหลัก (`/master`): ตัวเลขบนแท็บเป็น (0) จนกว่าจะกดเข้าแท็บ
เปิด `/master` จะเห็นแท็บ "สัญชาติ (0)", "ศาสนา (0)", "สถานภาพสมรส (0)", "ธนาคาร (0)" แต่เมื่อกดแท็บ "ธนาคาร" ระบบเรียก `GET /api/banks` แล้วตัวเลขเปลี่ยนเป็น "ธนาคาร (14)" และมีรายการครบ แสดงว่าตัวเลขเป็น 0 เพียงเพราะยังไม่เคยโหลด ทำให้ผู้ใช้เข้าใจผิดว่าไม่มีข้อมูล (หน้าฟอร์มเพิ่มพนักงานโหลด `/api/lookups/nationalities`, `/religions`, `/marital-statuses` ได้ข้อมูลปกติ)
**ผลที่ควรเป็น**: โหลดจำนวนของทุกแท็บตั้งแต่เปิดหน้า หรือซ่อนตัวเลขจนกว่าจะโหลด

### P2-7 คำขอ API ที่ timeout (ถูก axios ตัดที่ 15 วินาที) — ถือเป็น bug ตามที่ตกลงกัน
เกณฑ์: ช้าได้ แต่ต้องตอบกลับก่อน 15 วินาที ที่ตรวจพบ (ดูจาก Network ของหน้าเว็บ ค่า `duration` ~15,000ms และ status 0)

| Endpoint | หน้าที่เรียก | ผล |
|---|---|---|
| `GET /api/leave-balances/my-summary?year=2026&employeeId=1` | แดชบอร์ด `/`, ยอดวันลาคงเหลือ `/leave-balances` | timeout 2 ครั้ง ครั้งที่สำเร็จใช้ 9–10 วินาที (ช้าสุดในระบบ) |
| `GET /api/employees/:id` | `/employees/2`, `/profile` | timeout 1 ครั้ง (ดู P2-3) |
| `GET /api/my-salary/overview` | `/my-salary` | timeout 1 ครั้ง อีกครั้งสำเร็จที่ ~11 วินาที |
| `GET /api/salary/periods`, `/api/salary/overview`, `/api/salary/tax-brackets`, `/api/salary/employees/overview` | `/payroll` | timeout ทั้ง 4 ตัวในการเปิดครั้งหนึ่ง (ขณะนั้นมีหน้าอื่นกำลังโหลดพร้อมกันด้วย จึงควรทดสอบซ้ำแบบเปิดหน้าเดียว) |

ผลกระทบที่ผู้ใช้เห็น: ข้อมูลไม่ขึ้น ("ไม่พบข้อมูล"/การ์ดว่าง) พร้อมข้อความ "เซิร์ฟเวอร์ใช้เวลาประมวลผลนานเกินไป (timeout) ข้อมูลอาจถูกบันทึกแล้ว กรุณารีเฟรชหน้าเพื่อตรวจสอบ" ซึ่งไม่เหมาะกับคำขอแบบอ่านข้อมูล (ดู P2-3)
**จุดที่น่าจะต้องดู (backend)**: `my-summary` เป็นตัวที่ช้าและ timeout ที่สุด น่าจะมี query หนัก/หลายรอบ (N+1) ตรวจแผน query และ index; ฝั่ง frontend ควรมีปุ่ม "ลองใหม่" แทนที่จะให้ผู้ใช้รีเฟรชทั้งหน้า
**ตรวจหลังแก้**: เปิดแต่ละหน้าทีละหน้า ทุกคำขอข้างต้นต้องตอบกลับภายใน 15 วินาทีโดยไม่ถูกตัด

## P3 — LOW

1. **แถบ error ค้างหลังแก้แล้ว (ฟอร์มใบลา)** — กด "ยื่นคำขอลา" ตอนยังไม่เลือกประสงค์ขอลา จะขึ้นแถบแดง "กรุณาเลือกประสงค์ขอลา" แต่เมื่อเลือกประเภทลาและวันที่ลาแล้ว แถบแดงยังอยู่ ควรหายเมื่อค่าถูกต้อง นอกจากนี้แถบแสดงแค่ข้อผิดพลาดข้อแรก (ไม่บอกว่าวันที่ลายังไม่ได้เลือก)
2. **ข้อความตรวจสอบเป็นภาษาอังกฤษของเบราว์เซอร์** — หน้า `/login` กดเข้าสู่ระบบโดยไม่กรอก ขึ้น tooltip "Please fill out this field." ทั้งที่ทั้งระบบเป็นภาษาไทย ควรใช้ `noValidate` + ข้อความไทยของแอป (ฟอร์มเอกสารที่ใช้ `required` ของ HTML น่าจะเป็นแบบเดียวกัน)
3. **รูปแบบเลขเอกสารไม่ตรงกัน** — ใบขอหนังสือรับรองเดียวกันแสดงเป็น `CERT-4` ในหน้าประวัติเอกสารของพนักงาน แต่เป็น `CERT-0004` ในหน้าอนุมัติ และเลขที่ในเอกสารจริงเป็น `HR 0004/2569` ควรใช้รูปแบบเดียวกันทุกหน้า
4. **ชื่อตำแหน่งมีคำว่า "ตำแหน่ง" นำหน้าอยู่ในข้อมูล** — ชื่อตำแหน่งในระบบ เช่น `ตำแหน่งผู้จัดการฝ่ายทรัพยากรบุคคล` ทำให้ในเอกสารหนังสือรับรองกลายเป็น "ตำแหน่ง ตำแหน่งผู้จัดการฝ่าย..." ควรแก้ที่ข้อมูลตำแหน่ง (master data) ไม่ใช่ที่เทมเพลต
5. **ข้อความในหนังสือรับรอง** — "ออกให้เพื่อQA test - please ignore เท่านั้น" ไม่มีเว้นวรรคระหว่าง "เพื่อ" กับข้อความวัตถุประสงค์ และคอลัมน์ "วันที่ลา" ในประวัติเอกสารถูกใช้แสดง "วัตถุประสงค์: ..." สำหรับเอกสารที่ไม่ใช่ใบลา ควรเปลี่ยนหัวคอลัมน์หรือแยกตามประเภทเอกสาร
6. **ตรวจสิทธิ์การเข้าหน้า `/master` ไม่สอดคล้องกับเมนู (ให้ผู้ออกแบบยืนยัน)** — บัญชี `hr` ไม่เห็นเมนูข้อมูลหลักและตั้งค่าระบบ เมื่อพิมพ์ URL `/settings` ตรง ๆ ระบบแสดงหน้า "คุณไม่มีสิทธิ์เข้าถึงหน้าตั้งค่าระบบ" (ถูกต้อง) แต่พิมพ์ `/master` ตรง ๆ กลับเปิดและโหลดข้อมูลได้ (`GET /api/document-types` → 200) ถ้าตั้งใจให้ HR ใช้ได้ ให้เพิ่มเมนู ถ้าไม่ ให้ใส่ route guard เหมือน `/settings` และตรวจสิทธิ์ที่ API ด้วย
7. **ข้อมูลทดสอบไม่สอดคล้อง** — พนักงาน EMP0001 มีคำนำหน้า "นางสาว" แต่เพศ "ชาย" ในหน้ารายชื่อพนักงาน ฟอร์มสร้าง/แก้ไขควรเตือนเมื่อคำนำหน้าไม่ตรงกับเพศ (หรือแก้ข้อมูล seed)

## ข้อสังเกต (ไม่ถึงขั้น bug แต่ควรรู้)

- **ความเร็ว API**: เซิร์ฟเวอร์รันบนเครื่อง local จึงคาดว่าช้าอยู่แล้ว ความช้าอย่างเดียว (ไม่ถึง timeout) **ไม่นับเป็น bug** ตัวอย่างที่ช้าแต่สำเร็จ: `POST /api/leave-requests/my` ~10 วินาที, `GET /api/certificates/requests/:id/document` ~9 วินาที, `GET /api/employees/:id` 5–8 วินาที ส่วนกรณีที่ **timeout จริง ถือเป็น bug** ดูข้อ P2-7
- **เรียก API ซ้ำสองครั้งในทุกหน้า**: เกือบทุก endpoint ถูกเรียกซ้ำ 2 ครั้ง (เช่น `/api/organization/departments`, `/api/employees`, `/api/leave-requests/my`) น่าจะเป็น React Strict Mode ของ dev ที่ `useEffect` ไม่มี abort/cleanup (เกี่ยวข้องกับ P2-3) ให้ตรวจว่าบน production build ไม่เกิดซ้ำ
- `/api/notifications/summary` ถูกเรียกถี่ (10 ครั้งในช่วงที่ทดสอบ) ควรพิจารณาเพิ่มช่วง polling หรือใช้ cache
- **หน้า `/attendance/daily`**: วันที่เริ่มต้นเป็น 01/11/2569 (อนาคต) พร้อมข้อความ "ช่วงข้อมูลในไฟล์: 1–30 พฤศจิกายน 2569" และตารางว่าง ทั้งที่วันนี้คือ 7 ต.ค. 2569 ถ้าตั้งใจให้ใช้ช่วงของไฟล์ที่นำเข้าล่าสุด ควรบอกชัดเจน แต่ผู้ใช้ส่วนใหญ่คาดว่าจะเห็นวันนี้
- **หน้า `/ess/attendance`** (บันทึกเวลาของฉัน เดือน ต.ค.) แสดงเฉพาะ 1–2 ต.ค. ("วันทำงานทั้งหมด 2 วัน") ไม่มีวันที่ 5–7 ต.ค. และสถานะ "ยังไม่ลงเวลา" แต่ "ขาดงาน 0 วัน" ควรตรวจกติกาการนับวัน
- **หน้า `/my-salary`**: สลิป "ตุลาคม 2569" วันที่โอน 31 ต.ค. 2569 สถานะ "ปกติ" ปรากฏขณะที่วันนี้คือ 7 ต.ค. และ "ยอดสะสมทั้งปี (YTD) ม.ค.–ต.ค." เท่ากับยอดเดือนเดียว ถ้าเป็นข้อมูลทดสอบก็ไม่ต้องแก้ แต่โปรดตรวจ ป้ายกำกับ "ภาษีเงินได้หัก ณ ที่จ่าย (ภ.ง.ด. 91)" (ภ.ง.ด.91 เป็นแบบยื่นภาษีประจำปี ปกติหักรายเดือนใช้ ภ.ง.ด.1) และคำอธิบายรายได้ "เงินเดือนพื้นฐาน + เงินช่วยเหลือค่าที่พัก" ขณะที่การ์ดสัดส่วนแสดง "ค่าล่วงเวลา / เบี้ยขยัน 3,000"
- ฟอร์มใบลา: ปฏิทินเลือกวันที่ในอดีตได้ (1–6 ต.ค. ไม่ถูกปิด) และเงื่อนไขของลากิจระบุ "ยื่นล่วงหน้า 1 วัน" เนื่องจาก P1 ทำให้ยื่นไม่สำเร็จ จึงยังไม่ได้ทดสอบว่ากฎนี้ถูกบังคับหรือไม่ ให้ทดสอบหลังแก้ P1
